# Changelog

## [Unreleased]

- Fix `runTask`'s outer error handler stomping a task's phase to `'failed'` — with a misleading `SESSION_KILLED` error — out from under a legitimate, still-running retry. Retrying a task twice in quick succession (e.g. before the first retry shows any feedback) races inside the orchestrator: the second retry's `cancelPipeline` kills the first retry's session and registers a *fresh* pipeline for the same task ID before the first retry's now-rejected `executePhase()` promise is actually processed. By then `this.pipelines.has(taskId)` is true again, but it holds the second retry's pipeline, not the first's — a membership-only check (the one guarding this exact scenario, added for defect 7) can't tell the two apart, so it both logged the error and force-failed the task using its own stale pipeline reference while the second retry's session kept working in the background and could complete with a real verdict. `runTask`'s catch and `finally` blocks now compare pipeline identity (`this.pipelines.get(taskId) !== pipeline`), the same check `executePhase` already used for the equivalent race one layer in
- Fix dragging a task card to the "Review" kanban column silently running the coder instead of QA: `moveTaskToPhase`'s 'qa-review' target used to share `startPhaseFromArtifacts(hasPlan, hasSpec)` with the 'implement' target, which always resolves to `'implement'` once a plan exists — i.e. virtually every task past its first planning pass. Requesting `'qa-review'` now only falls back to an earlier phase when its own prerequisite (a plan) is actually missing; otherwise it honors `'qa-review'` directly
- Fix `rebaseOntoLatestDefault` (used at the start of every phase via `syncPhaseBaseline`, and directly in merge/create-pr/implement) and `reconcileDivergedBranch` (the QA-review unpushed-commits precheck) treating *any* failed `git rebase` as a real merge conflict and unconditionally spawning a merger agent session. A rebase can fail for reasons that have nothing to do with conflicting content — a dirty worktree, a stale git lock, a permission error — and in that case the merger session finds no unmerged files, resolves nothing, and reports "nothing to do," while the orchestrator's own log line had already asserted there was a conflict. Both functions now check for actual unmerged paths (`git diff --name-only --diff-filter=U`) before deciding a merger is warranted, and surface the real git error instead when there isn't one. The most common non-conflict cause — a dirty worktree left by a coder session that ended without committing, which blocks `git rebase` from even starting — is now also handled deterministically: both functions auto-commit it first (the same WIP-commit safety net already used in `implement.ts`'s COMMIT-GUARD and `artifact-commit.ts`'s pre-squash commit), so the rebase proceeds normally instead of ever reaching the conflict-or-not question. Both functions also now unconditionally reset any rebase/merge left in progress before doing anything else — a task's worktree has no writer but TeamAI's own sessions, so a stuck git operation here is always the leftover of one of our own sessions getting interrupted (most concretely: a merger killed mid-`git merge` by `recovery.ts`'s idle/tool stall sweep, which had no cleanup of its own), never an ambiguous external actor to reason about
- Fix the QA-rework subtask targeter (`writeQaFeedback` in `qa-feedback.ts`) silently dropping FAIL criteria that named a subtask by number or in a compound label (e.g. "AC-11 (CS-10/CS-11)", or an `additional_issues` meta-note like "plan.json marks subtask 11 as completed: true"): it only ever fuzzy-matched a criterion's own wording against each subtask's `acceptance_criteria[]` text, or an issue's `file` against `subtask.files[]` — neither path can resolve a criterion that references a subtask by id/label rather than reusing the plan's own acceptance-criteria phrasing, and the file-based path can't resolve a meta-issue about the plan itself. On a project seen in production, this meant two of five FAIL criteria (naming two subtasks QA had explicitly said must not be marked complete) were never dispatched for rework across a retry, while an unrelated already-PASSing subtask was incorrectly targeted and rejected for having nothing to fix. `qa_report.json`'s `criteria[]` and `additional_issues[]` entries now carry an optional `subtask_ids: number[]` field — `qa-review.md` instructs the QA agent to read `plan.json` and populate it per-criterion/issue by file overlap — which `writeQaFeedback` uses as the authoritative signal ahead of the old fuzzy matching, kept only as a fallback for reports written before this field existed
- Fix the task overview banner reporting "No specific QA findings were recorded" for a failed task whose QA report actually existed and had real per-criterion evidence, but had never reached a PASS/FAIL verdict (`overall: "IN_PROGRESS"`) — the QA tab already showed the full report, so the overview's silence looked like a missing report rather than an incomplete one. The overview now detects this case and surfaces which criteria QA did (and didn't) get to
- Fix the orchestrator treating a QA report stuck at `"IN_PROGRESS"` (the reviewer never reached a verdict) exactly like a genuine FAIL: it consumed the QA-attempt budget immediately, could fail the task on its very first attempt (`maxQaAttempts: 1` projects) with a misleading `qa-attempts-exhausted` reason, and would otherwise bounce to implement even though no criterion had actually failed — wasting a round on a report with nothing for the coder to fix. `qa-review.ts` now re-runs QA itself when `overall` is neither PASS nor FAIL, and fails with a distinct, honest `qa-incomplete` reason (no defect found, QA simply didn't finish) if the budget runs out first. Also fixed the QA tab silently dropping every criterion's `evidence` field (it only ever read `notes`, which this project's QA agent doesn't set)
- Fix the QA reviewer role backgrounding the full test suite and ending its turn to "wait for the completion notification" — a QA-review session gets exactly one turn and is torn down the instant it ends, so that notification never arrives and the run is killed mid-suite, leaving the report at `"IN_PROGRESS"` forever (see above). `qa-review.md` now mandates running the suite in the foreground, and the `qa-reviewer` role's Bash tool timeouts are raised (`BASH_DEFAULT_TIMEOUT_MS=600000`, `BASH_MAX_TIMEOUT_MS=1500000`, i.e. a 10-minute default and 25-minute ceiling instead of Claude Code's stock 2/10-minute defaults) so a full suite can actually complete inside that one turn without the agent needing to remember to pass an explicit `timeout` for the common case
- Fix PR creation failing on large specs ("Body is too long") by embedding a short spec summary in the PR body instead of the full spec.md, which is unbounded in size and could exceed GitHub's 65,536-character PR body limit
- Fix a wakeup-pending subtask (ADR 002 — e.g. a long verification sweep) being resumed immediately on server restart instead of waiting out its scheduled `wakeup_at`, which could burn through the deliverable-verification retry cap in minutes and fail the task despite a healthy background job
- Surface QA `spec_concerns` and `additional_issues` on the QA report tab, so a "PASS" report that still flags spec-level gaps or extra hard blockers is no longer visually misleading
- Fix a task getting stuck failing forever after a correct QA-fallback rework fix: the synthetic QA-rework subtask (id 9999) is no longer scope-rejected for fixing exactly what `qa_feedback.md` named, and completing it now reconciles the `completed` flag of any real subtask whose declared deliverables it happened to satisfy — unblocking that subtask's own dependents instead of leaving the implement-completeness gate checking a bookkeeping field nothing ever updates
- Fix the review panel being unable to distinguish a genuine QA pass from the spec phase auto-parking in `awaiting-review` (no-op revision, or a revision session that wrote `spec.md` but skipped `spec_summary.md`) — both land on the same phase with no visible reason, so an approver could wave a parked task straight into `create-pr`, which then fails trying to build the PR body. The `awaiting-review` event now carries an `awaitingReviewReason` (the same mechanism previously used only for failed-approval rollbacks, generalized and renamed from `approvalError`), surfaced as a "Needs attention" banner
- Fix `spec_summary.md` sometimes getting skipped by a revision-mode analyst session that stops right after verifying its own spec.md diff, without reaching the summary step after it: the spec/revision prompts now call out writing it as an explicit required step, and if it's still missing afterward the pipeline gives one focused follow-up session a chance to self-heal it (read the now-final spec.md, write just the summary) before parking for human review

## [0.1.0] — Initial Release

- Multi-agent Claude Code CLI orchestration with browser UI
- Kanban board for task management
- Automated pipeline: spec → plan → implement → QA → merge
- Auto mode for hands-free task processing
- Git worktree isolation for parallel agent sessions
- Rate-limit handling and crash recovery
- Project settings, provider configuration, and container support
- Electron desktop app with NSIS installer (Windows), DMG (macOS), AppImage/deb (Linux)
